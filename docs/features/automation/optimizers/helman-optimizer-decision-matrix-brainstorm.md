# Helman Automation — Optimizer Decision Matrix (brainstorm)

Status: proposal, not implemented. Outcome of a code-analysis + brainstorm session (2026-07-12).

## Goal

Make every automation run explainable: for each schedule slot and each optimizer in the
pipeline, show **what the optimizer saw (input), what it did (output), and why**.

Mental model — a matrix laid over the pipeline, where each cell behaves like a **PLC
function block**: inputs on the left edge, decision inside, outputs on the right edge
feeding the next block. One honest nuance from the code: optimizers output **only the
schedule**; the derived signals (surplus, SoC trajectory) are regenerated by an implicit
framework **rebuild block** between optimizers. The visualization must show that rebuild
step rather than pretending the optimizer emits surplus itself.

- **Rows**: schedule slots (30-min, rolling 48 h horizon from *now* → up to 96 rows;
  the horizon is inherently future-only, matching the "only future slots" requirement).
  Slot ids come from the existing horizon helpers (`iter_horizon_slot_ids` /
  `build_horizon_end` in `scheduling/schedule.py`) — reuse them; don't re-derive the grid.
- **Columns**: optimizer blocks in config/pipeline order, left → right, with **signal
  rail columns** in between showing the recomputed values each block actually received
- **Cells**: mini function block — decision + reason, inputs/outputs on its edges

## Decisions already made (brainstorm outcome)

| Question | Decision |
| --- | --- |
| UI home | New dedicated card `helman-automation-inspector` (precedent: `helman-solar-inspector`) |
| Capture mode | Trace recorded on **every** automation run, sparse encoding |
| History | **Last run only**, in-memory; matrix shows only the last run's future slots |
| Reason format | **Structured `code` + `params`**, formatted/localized by the frontend |
| Reason coverage | **Every (optimizer, slot) cell resolves to a reason in v1** — hybrid: window/ranking rationales are optimizer-emitted, slot-local predicate rationales are frontend-derived from recorded signals + config |
| Coverage enforcement | Runtime: **warn + synthetic `unexplained` fill, never fail the run**; step trace carries a `complete` flag; **hard assertions in per-optimizer contract tests** |
| Scheduling card | Per-slot "why" popover in the existing scheduling card is wanted too — sequenced after the inspector card, reusing the same trace |

## Current state (what the code gives us today)

- `AutomationRunner._async_execute_optimizer_loop_locked` (`automation/pipeline.py`) runs
  optimizers in config order and **rebuilds the full snapshot between steps** (forecasts,
  surplus, simulated SoC). The per-step inputs each optimizer saw therefore already exist
  in memory — they are just discarded.
- What survives into `AutomationRunResult`:
  - `OptimizerRunSummary` per optimizer: `id`, `kind`, `status`, `slots_written`
    (a diff **count**, computed by `_count_changed_writable_action_positions`),
    `duration_ms`, `error`
  - the **final** snapshot only (serialized by `snapshot_to_dict`)
- Exposed over websocket `helman/get_last_automation_run`; **no frontend consumer yet**.
- Ownership: optimizers silently skip user-owned action positions
  (`is_user_owned_inverter_action` / `is_user_owned_appliance_action`) — a distinct,
  interesting cell state ("wanted to write, blocked").

Key gap: nothing records *which* slots were touched, *what inputs* drove the choice, or
*why* slots were considered and rejected. `slots_written` is a bare count.

## Optimizer I/O inventory (verified against code)

### Signal taxonomy

Four kinds of signals, with very different pipeline behavior:

1. **Pipeline bus — the working schedule.** The only thing optimizers *write*. Every
   optimizer also reads it (ownership gate before writing). Flows block → block.
2. **Derived signals — recomputed by the framework rebuild after every step.** Read-only
   for optimizers. These are the rails whose values genuinely differ per column:
   - `batteryForecast.series[].socPct` — simulated SoC trajectory
   - `gridForecast.series[].availableSurplusKwh` — schedule-adjusted redirectable surplus
   - `adjustedHouseForecast` / forecast `status` + coverage — gating signal
3. **Static context — identical at every step** (pinned input bundle): `now`, import and
   export price forecasts, battery live state + params (usable capacity, efficiency, max
   charge power), day contexts (classification, `day_min_window`, `import_bands`),
   when-active demand profiles, recorder runtime hours (A2).
4. **Instance config params** — per block, constant.

### Read/write matrix

| Signal | export_price | charge_hold | surplus_appliance | charge_from_grid | daily_runtime |
| --- | :-: | :-: | :-: | :-: | :-: |
| **writes** → schedule | inverter `stop_export` | inverter `stop_charging` | appliance `on`/`mode` | inverter `charge_to_target_soc` | appliance `on`/`mode` |
| schedule (ownership gate) | R | R | R | R | R |
| export price forecast | **R** (threshold) | – | – | – | **R** (slot cost ranking) |
| import price forecast | – | – | – | **R** (cheap-window pick) | – |
| battery live state + params | – | **R** (needed kWh) | – | **R** (charge sizing) | – |
| derived: `socPct` trajectory | – | – | – | **R** ⚡ | – |
| derived: `availableSurplusKwh` | – | – | **R** ⚡ (per-bucket check) | – | **R** ⚡ (coverage tiebreak) |
| derived: forecast status/coverage | – | – | **R** (skip gate) | – | – |
| solar − baseline house (via `batteryForecast.series`) | – | **R** (surplus integral)¹ | – | – | – |
| day contexts | – | **R** (classification, `day_min_window`) | – | **R** (`import_bands`) | **R** (classification skip guard) |
| when-active demand profile | – | – | **R** (required kWh) | – | **R** (energy sizing) |
| runtime hours history (A2) | – | – | – | – | **R** (remaining hours) |

⚡ = **step-sensitive**: the value genuinely depends on what earlier optimizers wrote.
¹ `charge_hold` reads `solarKwh`/`baselineHouseKwh` from the rebuilt battery forecast, but
solar and *baseline* house are unaffected by schedule changes — effectively static.

### The interesting consequence for visualization

Only **three** of five blocks consume step-sensitive rails: `surplus_appliance` and
`daily_runtime` (surplus), `charge_from_grid` (SoC). `export_price` and `charge_hold`
would decide identically at any pipeline position (given the same config). The block
diagram can encode this honestly: step-sensitive input pins connect to the recomputed
rail *after* the previous rebuild; static pins drop down from a shared static-context
rail. That is exactly the "surplus only once in the first column doesn't represent
reality" correction — surplus and SoC are rails with a **new value segment after every
rebuild block**, and each optimizer taps the segment in front of it.

## Unified optimizer block (PLC-style)

Every block renders with the same frame and pin layout; unused pins are hidden or dimmed.
Kind-specific content lives only in the body mini-visualization.

```text
   static rails ────────┬───────────────────────┬──────────────
   (prices, battery,    │                       │
    day ctx, history)   ▼                       ▼
                ┌───────────────────┐   r   ┌───────────────────┐
 schedule ═════▶│ ⏸ charge_hold     │══════▶│ ⛔ export_price    │═══▶ …
                │   "hold-morning"  │   e   │   "avoid-negative"│
 surplus  ─────▶│ ok · 6 writes 12ms│   b   │ ok · 4 writes 3ms │
 SoC      ─────▶│ ┌───────────────┐ │   u   │ ┌───────────────┐ │
                │ │ kind-specific │ │   i   │ │ kind-specific │ │
                │ │   mini-viz    │ │   l   │ │   mini-viz    │ │
                │ └───────────────┘ │   d   │ └───────────────┘ │
                │ params: 06–12,    │  ───▶ │ params:           │
                │  target 80% ±10%  │ surplus′ when_price<0.0   │
                └───────────────────┘  SoC′ └───────────────────┘
```

- **Left pins**: schedule bus (thick), then only the signals that kind reads (from the
  I/O matrix above). Step-sensitive pins (⚡) tap the rail segment produced by the
  previous rebuild; static pins tap the static rail.
- **Right edge**: schedule bus out + trace outputs (writes count, decisions).
- **Rebuild connector** between blocks: a thin framework-owned element that recomputes
  the surplus/SoC rail segments. Hovering it shows "what changed here" (e.g. "surplus
  08:00–11:00 dropped 3.1 → 1.7 kWh because boiler was scheduled").
- **Body header**: kind icon + instance id + `OptimizerRunSummary` (status, writes,
  duration). Body footer: key config params. Clicking opens the full detail panel
  (all params, run-level notes, decision list).

## Data model

### Three capture layers

1. **Framework-recorded writes (ground truth, zero optimizer changes).**
   Upgrade the existing per-step diff (`_count_changed_writable_action_positions`) from a
   count to records: `{slotId, domain ("inverter" | "appliance:<id>"), before, after}`.
   Caveat: this diff only sees **committed** writes. A "wanted to write but blocked by a
   user-owned position" event is invisible to the framework — the optimizer's ownership
   gate suppresses the write *inside* `optimize()` before the diff runs. `blocked` is
   therefore necessarily an **optimizer-emitted** decision (layer 3), not something the
   framework can reconstruct from the write diff.

2. **Framework-recorded signal rails.**
   - **Static rails**, captured once per run: import price, export price, solar kWh,
     baseline house kWh per slot.
   - **Step-sensitive rails**, captured per rebuild (i.e. before each step and after the
     last): `availableSurplusKwh` and projected `socPct` per slot. These are the rail
     segments the block diagram and the matrix's inter-column values render.
   - Forecasts run on 15-min canonical buckets vs 30-min schedule slots; the trace
     aggregates buckets to slot granularity (sum for energies, end-of-slot for SoC).

3. **The "why" — dense coverage in v1, via a hybrid of emitted and derived reasons.**
   Every (optimizer, slot) cell must resolve to a reason, but not every reason must be
   emitted by the optimizer. Reasons come from two sources:

   - **Emitted decisions** — required wherever the rationale is *not* a function of the
     slot's own signals: window-level computations (`charge_hold` release slot,
     `charge_from_grid` bridging), rankings (`daily_runtime` cheapest-first), and every
     `applied` / `blocked` group. Group-encoded: one decision covers a slot list sharing
     one rationale, so these stay cheap.
   - **Derived reasons** — slot-local predicate rationales the frontend computes at
     popover-open time from data already in the payload: rail arrays, static rails,
     config params, and the serialized snapshot context (e.g. demand profiles). Each
     optimizer kind registers its derivation rules next to the reason formatter.
     Examples: `export_price` rejected = export price ≥ threshold (static rail +
     config); `surplus_appliance` rejected = surplus rail < demand requirement + buffer.

   This keeps the emission burden small exactly where per-slot reasons would be
   numerous, while the genuinely non-derivable rationales are recorded at the source:

   ```text
   trace.decision(
       slot_ids=[...],                      # 1..n slots sharing one rationale
       outcome="applied" | "rejected" | "blocked" | "out_of_scope",
       action={"domain": "inverter", "kind": "stop_charging"},   # only for applied/blocked
       reason={"code": "hold_window_applied", "params": {...},
               "signals": ["availableSurplusKwh"]},              # optional per-slot enrichment
   )
   trace.note(code=..., params=...)         # run-level (e.g. battery params missing)
   ```

   Emission rules per step:
   - `applied` groups for every write — always emitted; ground-truth writes must be
     explained at the source
   - `blocked` when a user-owned position stopped a write
   - emitted `rejected` / `out_of_scope` groups for window/ranking rationales
   - everything else falls into the kind's **declared derivable space** — slots the
     frontend explains by rule; the optimizer emits nothing for them
   - run-level `note`s (e.g. "battery params missing") expand to one horizon-wide
     `out_of_scope` group so the whole column stays explained

   **Per-slot params without duplication**: a group reason may carry shared params
   (threshold, needed kWh) plus a `signals` list naming rails; the frontend pulls the
   slot-specific value from the rail arrays when rendering ("price −0.05 < 0.00").

   **Drift risk (accepted trade-off)**: a derivation rule duplicates an optimizer
   predicate in the frontend; if the backend condition changes, the derived explanation
   can go stale and explain the decision wrongly. Mitigation: one derivation-rules
   module per kind, colocated with the reason formatter, pinned by the same contract
   tests that pin the reason catalogue.

### Optimizer contract change

`optimize(snapshot, config)` → `optimize(snapshot, config, trace)`.

A recorder parameter (rather than a richer return type) is preferred because reasons are
computed deep inside helper functions (`_resolve_release_slot`, `_find_candidate_slot_ids`,
…) and threading return values up through them is noisy. The recorder is a dumb appender;
the framework owns serialization, coverage validation, and the write diff as ground truth.

**Recorder ownership + failure-path survival.** The trace is owned by
`_async_execute_optimizer_loop_locked` (one `OptimizerTrace` per run), *not* by
`_PipelineExecutionResult`. This matters because the loop has two paths that do **not**
return an `execution_result`:

- `_OptimizerExecutionError` (a hard optimizer failure aborts the run) — the result is
  built in `run()`'s `except` branch.
- the top-level `except Exception` in `run()`.

The trace must be attached to the `AutomationRunResult` on **those paths too**, so a
failed/aborted run still renders whatever was captured before the abort (the failing
column badged from `OptimizerRunSummary.status`). Concretely: the loop accumulates the
trace as it goes and stashes it where both the success return and the error paths can
reach it (e.g. carried on `_OptimizerExecutionError` alongside `snapshot`, and threaded
into `_build_runner_failed_result`). Partial-run inspection is the highest-value case, so
the trace is a first-class output of the loop, not a by-product of the happy path.

**Skipped optimizer (`SurplusApplianceSkip`).** `optimize()` can raise
`SurplusApplianceSkip` *mid-run*, after the recorder may already hold partial decisions.
On skip the framework **discards that optimizer's partial decisions** and collapses its
column to a single horizon-wide `skipped` note (same expansion mechanism as run-level
`note`s → column-wide `out_of_scope`). The coverage validator treats a `status="skipped"`
column as fully explained — it does **not** run the gap check for that step, so a bailed
optimizer never produces an `unexplained` flood. Note the skip branch also performs its
own snapshot rebuild before `continue`ing (restoring user-owned appliance actions); the
`railsIn` for a skipped step is captured from the snapshot the step *received*, and the
rebuilt segment it produces feeds the next step normally.

### Coverage enforcement

Trace completeness is a contract, but observability must never take down the automation:

- **Runtime — warn + synthetic fill, never fail the run.** After each step the framework
  checks that every horizon slot is covered by an emitted decision or the kind's declared
  derivable space. Gaps log a WARNING and are filled with a synthetic
  `{code: "unexplained"}` decision, so the UI invariant "every cell is clickable and says
  something" holds unconditionally. The step's trace is marked `complete: false` and the
  optimizer's block in the pipeline header shows a badge. Hard-failing the run over a
  missing explanation is explicitly rejected — an instrumentation bug in the diagnostics
  layer must not stop the battery from charging.
- **Skipped optimizers are exempt from the gap check.** A `status="skipped"` step (e.g.
  `SurplusApplianceSkip`) is fully explained by its single horizon-wide `skipped` note;
  the validator does not run the per-slot gap check for it. See the skip-path handling in
  the contract-change section.
- **Overlaps warn too.** Two decisions in one step claiming the same slot is almost
  always an instrumentation bug, not intent: later emission wins for rendering, and the
  validator warns the same way it does for gaps.
- **Writes must be explained.** A framework-recorded write (layer 1, ground truth) with
  no covering `applied` decision is a stronger bug signal than an uncovered untouched
  slot — the optimizer did something it did not explain. Louder warning; the UI renders
  the action chip with an "unexplained" marker rather than hiding the write.
- **Tests — hard enforcement.** A shared assertion helper used by the existing
  `test_automation_optimizer_*.py` scenario tests asserts exhaustive coverage and
  write/decision consistency, so a violation costs a red build instead of a broken run.
  New optimizer kinds cannot ship uninstrumented.

### Reason catalogue (v1 contract)

This table is the **v1 contract**: the codes and their E/D source are what the
contract-test helper pins. Params are still examples and may be tuned during
implementation, but adding/removing a code or flipping its source is a contract change.

Source: **E** = emitted by the optimizer, **D** = derived by a frontend rule from
recorded rails + config + snapshot context. The E/D split is load-bearing for phasing:
optimizers whose `rejected` case is **D** (`export_price`, `surplus_appliance`) emit only
`applied`/`blocked`/notes on the backend — their rejection reason is a frontend derivation
rule, not backend emission work.

| --- | --- | :-: | --- |
| export_price | `price_below_threshold` (applied) | E | `threshold`; per-slot price via `signals` |

| export_price | `stop_export_unsupported` (note → out_of_scope) | E | `skippedSlots` |
| charge_hold | `hold_window_applied` | E | `neededKwh`, `marginPct`, `releaseSlot`, `boundBy` (`surplus` \| `day_min_window` \| `window_end`) |

| charge_hold | `day_not_matched` (out_of_scope, per day) | E | `classification`, `onlyOnDays` |
| charge_hold | `battery_params_missing` (note → out_of_scope) | E | — |
| charge_from_grid | `bridge_window` (applied) | E | `expensiveWindow`, `deficitKwh`, `targetSoc` |
| charge_from_grid | `cheaper_slot_chosen` (rejected) | E | `chosenPrice`; per-slot price via `signals` |

### Serialized shape (sketch)

Attached to `AutomationRunResult.to_dict()` as `trace`; travels over the existing
`helman/get_last_automation_run`. Parallel arrays keyed by `slotIds` keep it compact.

```jsonc
"trace": {
  "slotIds": ["2026-07-12T06:00:00+02:00", ...],          // ≤ 96, future-only by construction
  "staticRails": {
    "importPrice": [...], "exportPrice": [...],
    "solarKwh": [...], "houseKwh": [...]
  },
  "steps": [
    {
      "optimizerId": "hold-morning-charge",
      "kind": "charge_hold",
      "complete": true,                                    // false when synthetic fill happened
      "railsIn": {                                         // rail segment BEFORE this block
        "availableSurplusKwh": [...],
        "batterySocPct": [...]
      },
      "writes": [                                          // framework diff (layer 1)
        {"slotId": "...", "domain": "inverter",
         "before": null, "after": {"kind": "stop_charging", "setBy": "automation"}}
      ],
      "decisions": [                                       // dense, group-encoded (layer 3)
        {"slotIds": ["...", "..."], "outcome": "applied",
         "action": {"domain": "inverter", "kind": "stop_charging"},
         "reason": {"code": "hold_window_applied",
                    "params": {"neededKwh": 8.2, "releaseSlot": "10:30", "boundBy": "surplus"}}},
        {"slotIds": ["..."], "outcome": "out_of_scope",
         "reason": {"code": "after_release", "params": {"releaseSlot": "10:30"}}}
      ],
      "notes": [ {"code": "...", "params": {...}} ]
    }
  ],
  "railsFinal": { "availableSurplusKwh": [...], "batterySocPct": [...] }
}
```

Size estimate: static rails 96×4 floats, step rails 96×2 floats × (steps+1), dense
decisions as a few dozen group objects → roughly 40–100 KB JSON. Acceptable next to the
already-large serialized snapshot in the same payload; always-on recording is fine.

## UI — `helman-automation-inspector` card

### Layout

Top: the PLC block diagram (blocks + rebuild connectors + rails, as specified above) —
this is the pipeline overview and doubles as the column header for the matrix below.
Bottom: the matrix. Each optimizer column is flanked by the step-sensitive rail values
(`S` surplus kWh, `⚡` SoC %) it actually received — the inter-column values change when
an earlier block's writes moved them.

```text
┌────────────────────────────────────────────────────────────────────────────────────┐
│  Automation run · today 06:00 · completed · 412 ms                    [Run now]    │
│                                                                                    │
│  [ PLC block diagram: blocks, rebuild connectors, static + derived rails ]         │
├───────┬──────────────┬───────────┬────────────┬───────────┬────────────┬───────────┤

│       │ ↑imp ↓exp ☀  │ S  ⚡SoC  │            │ S  ⚡SoC  │ appliance  │           │
├───────┼──────────────┼───────────┼────────────┼───────────┼────────────┼───────────┤
│ ── Sat 12 Jul · surplus day ───────────────────────────────────────────────────────│
│ 06:00◀│ 2.10 0.41 0.0│ 0.0  41%  │     ·      │ 0.0  41%  │ ▢ low surp │    —      │
```

(Note the 10:00 row: `rails₁` surplus dropped 2.2 → 1.1 because the boiler got scheduled
at 09:30 — the pipeline effect visible in the row itself.)

- Rail columns show only step-sensitive signals (surplus, SoC). Static inputs stay in one
  left column — per the I/O inventory they genuinely never change; per-block relevance is
  conveyed by the block's pins and the cell popover.
- Rail columns are collapsible (e.g. show only where values changed vs the previous rail)
  to keep the matrix readable with 5+ optimizers.
- **Final column**: resulting persisted action + `setBy`, reusing the scheduling card's
  action presentation model (`schedule-action-presentation.ts`) for icons/colors/labels.
- **Row grouping**: by local day with day-context classification in the group header
  (`dayContexts` already in the payload). "Only rows with activity" filter; `◀ now`
  marker. Rows cover only the run horizon — future slots by construction.

### Cell visual language

Since v1 guarantees dense reasons, *every* cell is clickable and explainable:

| State | Rendering | Source |
| --- | --- | --- |
| out of scope | faint `·` (reason on click) | `out_of_scope` decision or derivation rule |
| wrote action | filled action chip (icon + color per action kind) | `applied` + framework write |
| evaluated, not chosen | hollow/outlined chip `▢` with short label | `rejected` decision or derivation rule |
| blocked by user-owned | lock icon chip | `blocked` decision |
| unexplained | glyph with `?` warning marker (write chip keeps its action icon) | synthetic fill / write without `applied` |
| optimizer skipped/failed | whole column greyed, header badge | `OptimizerRunSummary.status` |

Interactions:

- **Click a cell** → popover rendered as the unified block zoomed to one slot: left pins
  show the actual input values for this slot (rail values + relevant static values),
  center shows the formatted reason, right shows action before/after.
- **Hover a cell** in a group decision → highlight sibling slots of the group in the same
  column (charge_hold's hold window reads as one visual block).
- **Hover a rebuild connector / rail column** → highlight slots where the rail changed,
  with old → new values.

## Implementation phases (sketch, for a later plan doc)

1. **Backend trace plumbing** — `OptimizerTrace` recorder, protocol change, framework
   write-diff upgrade, static + per-step rail capture, serialization into
   `AutomationRunResult["trace"]`, coverage validator (warn + synthetic fill +
   `complete` flag).
2. **Reasons (v1-mandatory)** — emitted decisions per the catalogue, scoped by the E/D
   split: `applied`/`blocked` groups + notes in all five optimizers; window/ranking
   `rejected`/`out_of_scope` rationales only where the catalogue marks them **E**
   (`charge_hold`, `charge_from_grid`, `daily_runtime`). `export_price` and
   `surplus_appliance` emit no `rejected` groups — their rejection is a **D** frontend
